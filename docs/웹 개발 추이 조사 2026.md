# 빌드 없이도 충분해진 브라우저를 로그 변환기에 들여오기

2025~2026년 웹 프론트엔드의 가장 큰 변화는 **"예전에는 라이브러리나 빌드 도구가 있어야 하던 일을 이제 브라우저가 기본 기능으로 해 준다"**는 점입니다. 대화상자(`<dialog>`), 접었다 펴는 설정 묶음(`<details name>`), 버튼 하나로 창을 여는 invoker commands, 다크 모드 색을 한 줄로 정하는 `light-dark()`, CSS 중첩과 `:has()`가 2026년 9월 기준 모두 Baseline(주요 브라우저 공통 지원) 안에 들어왔습니다. 그래서 `index.html` 한 파일로 동작하는 코코포리아 로그 변환기는 새 프레임워크를 도입할 이유가 없고, 브라우저 기본 기능으로 JS와 CSS를 줄이는 방향이 맞습니다. 우선 할 일은 다섯 가지입니다. 첫째, **도구 화면의 테마를 "시스템/밝게/어둡게" 세 가지 중에서 고르게 하고 깜빡임 없이 적용합니다.** 둘째, **내보낸 HTML이 보는 사람의 OS 설정을 따라가게 합니다.** 셋째, **캐릭터 글자색을 테마마다 대비 4.5:1 이상으로 자동 보정합니다.** 넷째, **자동 저장과 복원을 붙입니다.** 다섯째, **수천 줄 로그를 위해 `content-visibility`를 적용합니다.** 티스토리용 코드는 인라인 스타일만 살아남기 때문에 "도구 화면은 최신 기능, 내보내는 코드는 보수적으로"라는 이중 전략이 필요합니다. 인라인 스타일에서도 `color-scheme`와 `light-dark()`는 쓸 수 있으므로 미디어쿼리 없이 양쪽 테마를 지원할 수 있는 길은 있습니다. 다만 이 방법은 티스토리에서 직접 확인한 결과가 아니라 추론이므로 반드시 시험해 봐야 합니다.

## 2026년 9월, 설정 패널과 미리보기에 필요한 기능은 거의 다 Baseline입니다

"Baseline"은 Chrome·Edge·Firefox·Safari(데스크톱과 모바일) 최신판이 모두 지원하는 기능이라는 공식 표시입니다. **Newly available**은 모든 최신판이 막 지원하기 시작했다는 뜻이고, 그 날로부터 **30개월**이 지나면 **Widely available**이 되어 구형 기기까지 안심하고 쓸 수 있다는 뜻이 됩니다. 아래 상태는 Baseline의 원본 데이터인 `web-features` v3.40.0(2026-09-24 배포)에서 직접 조회한 값입니다. 이 데이터에 실린 최신 브라우저는 Chrome 154, Firefox 156, Safari 27입니다 ([npm: web-features](https://www.npmjs.com/package/web-features); [Web platform features explorer](https://web-platform-dx.github.io/web-features-explorer/)).

| 구분 | 기능 | 이 도구에서 쓰는 곳 | 가장 늦게 지원한 Safari |
|---|---|---|---|
| **Widely (마음껏 사용)** | `color-scheme`, `<dialog>`, `@layer`, dvh/svh, 컨테이너 쿼리, oklch/`color-mix()`, CSS 중첩, `:has()`, `:user-invalid` | 테마 기본값, 대사 수정 창, 모바일 높이, 미리보기 폭 대응, 색 섞기 | 13~17.2 |
| **Newly (최신 브라우저면 안전)** | `light-dark()`, `text-wrap: balance`, `@property`, `@starting-style`, `<details name>`, 상대 색 문법, `scrollbar-gutter`, Popover, 같은 문서 View Transitions, invoker commands, 컨테이너 스타일 쿼리, `field-sizing: content` | 다크 모드 토큰, 설정 아코디언, 창 열기 애니메이션, 입력창 자동 높이 | 17.2~26.2 |
| **아직 Baseline 아님** | `text-wrap: pretty`(Firefox 없음), `<dialog closedby>`(Safari 없음), `popover="hint"`, `interpolate-size`/`calc-size()`(Chromium만), 커스텀 `<select>`(Firefox 없음), 스크롤 연동 애니메이션 | 있으면 좋고 없어도 되는 장식 | — |

([npm: web-features](https://www.npmjs.com/package/web-features))

이 도구에 특히 중요한 날짜가 몇 개 있습니다. **`light-dark()`는 2024-05-13에 Newly가 되었고 약 2026-11-13에 Widely가 됩니다.** 다크 모드 표준 수단이 두 달 뒤면 "구형 기기까지 안전" 단계에 들어간다는 뜻입니다. **invoker commands(`<button commandfor="edit" command="show-modal">`)는 2025-12-12에 Safari 26.2가 지원하면서 Baseline이 되었습니다.** 대사 수정 창을 여는 JS를 HTML 속성으로 바꿀 수 있습니다 ([InfoQ](https://www.infoq.com/news/2026/01/html-invoker-commands/); [MDN Invoker Commands API](https://developer.mozilla.org/en-US/docs/Web/API/Invoker_Commands_API)). 입력 내용에 맞춰 입력창 높이를 늘려 주는 **`field-sizing: content`는 2026-06-16에 Firefox 152가 지원하면서 막 Baseline이 되었습니다** ([web-features explorer: field-sizing](https://web-platform-dx.github.io/web-features-explorer/features/field-sizing/)).

반대로 조심할 기능도 있습니다. 배경을 누르면 창이 닫히게 하는 `<dialog closedby="any">`는 Safari 27에서도 지원하지 않습니다. 따라서 "배경 클릭 시 닫기" JS 몇 줄을 그대로 남겨 두어야 합니다 ([MDN closedBy](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/closedBy)). 앵커 포지셔닝(말풍선을 버튼 옆에 붙이는 기능)은 자료끼리 판정이 엇갈립니다. web.dev와 MDN은 Firefox 147(2026-01)로 Baseline이 되었다고 했지만, `web-features` 데이터는 여전히 "Baseline 아님"으로 표시합니다 ([web.dev: January 2026](https://web.dev/blog/web-platform-01-2026); [npm: web-features](https://www.npmjs.com/package/web-features)). 핵심 속성은 세 엔진 모두 동작하지만, 이 도구에서 꼭 필요한 기능은 아니므로 미뤄도 됩니다.

흐름 자체도 이 방향을 뒷받침합니다. State of CSS 2025에서 **`:has()`는 사용률과 선호도 모두 1위**였고, `:has()`, 컨테이너 쿼리, subgrid는 "바라는 기능"에서 "매일 쓰는 기능"으로 넘어갔다고 평가되었습니다 ([State of CSS 2025](https://2025.stateofcss.com/en-US/features/)). 2026년 2월에는 Apple·Google·Microsoft·Mozilla·Igalia가 **19개 중점 영역**의 Interop 2026을 발표했습니다. 여기에는 앵커 포지셔닝, 컨테이너 스타일 쿼리, View Transitions가 들어 있어 연내에 브라우저 간 차이가 더 줄어들 전망입니다 ([web.dev: Interop 2026](https://web.dev/blog/interop-2026)). ES 모듈과 import maps도 모든 브라우저가 지원하므로, Preact 같은 라이브러리조차 공식 "빌드 없는 작업 방식" 가이드를 냅니다 ([Preact No-Build Workflows](https://preactjs.com/guide/v10/no-build-workflows/)). 비교 대상인 한국 도구들을 보면 CCFOLIA-Log-Backup은 React+Vite+Tailwind로 빌드하고, Eon 변환기는 이 도구처럼 단일 `index.html`로 동작합니다 ([CCFOLIA-Log-Backup](https://github.com/660-099/CCFOLIA-Log-Backup); [eon-ccfolia-log-converter](https://github.com/Eon-00/eon-ccfolia-log-converter)). 단일 파일 방식은 시대에 뒤처진 것이 아니라, 브라우저가 따라와 준 덕분에 오히려 가벼운 선택이 되었습니다.

실제로 쓰는 원칙은 간단합니다. 지원하지 않는 CSS 속성은 브라우저가 조용히 무시합니다. 그래서 `text-wrap`, `@starting-style`, View Transitions처럼 "없으면 그냥 밋밋해지는" 기능은 대비책 없이 넣어도 됩니다. 반면 `closedby`나 `field-sizing`처럼 없으면 기능이 빠지는 것은 `CSS.supports()`나 속성 존재 여부로 확인한 뒤 짧은 JS 대체 코드를 둡니다. 예를 들어 `field-sizing`을 지원하지 않으면 `el.style.height = el.scrollHeight + 'px'`로 높이를 맞춥니다. 이 대체 패턴들은 여러 자료를 종합한 일반적인 기법이며, 이번 조사에서 직접 실행해 본 것은 아닙니다.

## 다크 모드는 "세 가지 선택지 + head 속 한 줄 스크립트"로 푼다

현재 `index.html`은 `@media (prefers-color-scheme: dark)`로 OS 설정만 따릅니다. 2025~2026년 표준 구성은 여기서 한 걸음 더 나아갑니다. 사용자의 선택을 **"light / dark / system" 세 값**으로 localStorage에 저장하고, "system"일 때만 OS 설정을 따르며, 탭을 열어 둔 동안 OS 설정이 바뀌어도 계속 반영하는 방식입니다. localStorage가 막힌 환경(사생활 보호 모드 등)에서도 오류가 나지 않도록 try/catch로 감싸고, 실패하면 시스템 설정으로 돌아갑니다 ([goilerplate: Dark mode without the flash](https://goilerplate.com/blog/dark-mode-without-flash)).

페이지를 열 때 잠깐 흰 화면이 번쩍이는 현상을 "FART(Flash of inAccurate coloR Theme)"라고 부릅니다. 원인은 저장된 테마를 읽는 JS가 첫 화면이 그려진 **뒤에** 실행되기 때문입니다 ([CSS-Tricks](https://css-tricks.com/flash-of-inaccurate-color-theme-fart/)). 확실한 해결책은 하나뿐입니다. `<head>` 맨 위, 스타일시트보다 먼저, **즉시 실행되는 작은 인라인 스크립트**를 두고, 거기서 `<html>`에 `data-theme`와 `color-scheme`를 설정하는 것입니다 ([DEV: Prevent the Flash of Wrong Theme](https://dev.to/137foundry/how-to-prevent-the-flash-of-wrong-theme-when-implementing-dark-mode-2pg1); [DEV: Why MUI Avoids Theme Flash](https://dev.to/mohsenfallahnjd/why-mui-avoids-theme-flash-on-first-load-darklight-mode-4ek)). 흔한 실수도 하나 있습니다. 첫 방문 때 기본값("light")을 저장소에 **써 버리면** 이후 OS 설정을 영영 무시하게 됩니다. 사용자가 직접 고르기 전에는 아무것도 저장하지 않아야 합니다 ([GitHub issue #1586](https://github.com/StellarEdu/StellarEduPay/issues/1586)).

CSS 쪽 설정은 짧습니다. `:root{color-scheme: light dark}`를 선언하고 색 토큰을 `--bg: light-dark(#fafafa, #121212)`처럼 한 번씩만 적습니다. 수동 선택은 `:root[data-theme=dark]{color-scheme: dark}`로 덮어씁니다. `light-dark()`는 "현재 color-scheme가 무엇인지"를 보고 색을 고르기 때문에, OS 설정이든 사용자 토글이든 같은 선언 하나로 처리됩니다 ([web.dev: light-dark()](https://web.dev/articles/light-dark)). 게다가 `color-scheme`만 바르게 설정하면 체크박스, 스크롤바, 입력창 같은 기본 부품도 저절로 어두워집니다. `<meta name="color-scheme" content="light dark">`를 함께 넣으면 CSS를 읽기 전에도 바탕색이 맞춰져 깜빡임이 더 줄어듭니다. 다만 이 meta 동작은 공식 문서를 직접 열람하지 못해 교차 확인하지 못했습니다.

미리보기 iframe에는 이 도구만의 함정이 있습니다. CSS 표준 그룹은 "iframe 안 문서의 color-scheme가 바깥과 다르면 iframe에 불투명한 바탕을 깐다"고 정했습니다. 그래서 Chrome에서는 **어두운 도구 화면 안에 흰 상자가 뜨는** 식의 어긋남이 생깁니다. Firefox는 이렇게 동작하지 않는다는 보고가 있습니다 ([Florens Verschelde: Transparent iframes and dark mode](https://fvsch.com/transparent-iframes); [Mozilla Bugzilla 1738380](https://bugzilla.mozilla.org/show_bug.cgi?id=1738380)). 또 iframe 안의 `prefers-color-scheme`는 OS가 아니라 **바깥 페이지에서 iframe 요소에 걸린 color-scheme**를 따릅니다 ([MDN prefers-color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-color-scheme)). 이것을 역이용할 수 있습니다. 미리보기 영역에 "보는 사람 기준 밝게/어둡게" 전환 버튼을 달고 `<iframe style="color-scheme: dark">`처럼 바꿔 주면, 내보낸 HTML이 다크 모드 독자에게 어떻게 보일지를 **실제 OS 설정을 바꾸지 않고도** 확인할 수 있습니다 ([Simon Elvery: What colour is that iframe?](https://elvery.net/drzax/iframe-background-colour-transparent-dark-mode/)). 이 활용법은 문서화된 동작을 바탕으로 한 추론입니다.

내보낸 HTML 파일은 JS 없이 **보는 사람의 OS 설정을 따르는 것**을 기본값으로 삼는 편이 좋습니다. 내보낸 파일은 카카오톡이나 디스코드의 인앱 브라우저처럼 오래된 환경에서도 열릴 수 있고, `light-dark()`가 Widely가 되는 것은 2026년 11월이기 때문입니다. 그래서 **`@media (prefers-color-scheme: dark)`로 CSS 변수를 바꾸는 방식을 기본으로 깔고, `light-dark()`는 그 위에 얹는 정도**가 가장 튼튼합니다. 설정에는 "내보내기 테마: 자동(보는 사람 따라) / 밝게 고정 / 어둡게 고정" 세 가지를 두는 것을 권합니다. 현재 도구의 배경 선택지 "밝게 / 어둡게 / 종이"는 "고정" 쪽에 해당하므로, 여기에 "자동"을 하나 더하는 셈입니다. 이 부분은 조사 노트의 종합 추론입니다.

### 티스토리 코드: 미디어쿼리 없이 양쪽 테마를 버티는 방법

티스토리에 붙이는 코드는 `<style>` 블록과 미디어쿼리를 쓸 수 없고 `style=""` 속성만 남습니다. 여기서 쓸 수 있는 수가 하나 있습니다. `color-scheme`와 `light-dark()`는 **속성값**이지 규칙이 아니므로, 인라인 스타일 안에서도 동작합니다. 로그 전체를 감싸는 상자에 `style="color-scheme: light dark; background: light-dark(#fff,#1b1b1b); color: light-dark(#222,#e6e6e6)"`처럼 적으면, 이론상 미디어쿼리 없이 독자의 OS 설정에 따라 색이 바뀝니다. 구형 브라우저에서는 `light-dark()`를 모르면 그 선언만 버려지므로, 같은 style 안에 `color:#222; color:light-dark(#222,#e6e6e6)`처럼 **일반 색을 먼저 쓰고 덮어쓰는** 방식으로 대비할 수 있습니다.

다만 이것은 CSS 동작 원리에서 끌어낸 추론이며, 조사 노트에는 티스토리 편집기가 이 속성들을 지우는지에 대한 자료가 없습니다. 걸림돌도 두 가지 있습니다. 첫째, 블로그 스킨이 자체 다크 모드를 클래스로 켜고 끄는 경우, 로그 상자는 OS만 따르므로 스킨과 어긋날 수 있습니다. 둘째, 상자 밖(스킨 배경)과 대비가 맞지 않을 수 있습니다. 그러므로 **로그 상자가 항상 자기 배경색을 갖게 하고**, 티스토리용 기본값은 "밝게 고정"으로 두되 "자동(실험적)"을 선택지로 제공하는 것이 안전합니다. 실제 티스토리 글쓰기 HTML 모드에 붙여 넣어 저장·발행한 뒤 style 속성이 남아 있는지 확인하는 테스트가 먼저 필요합니다.

## 16px, 행간 1.7, 아이콘 40px: 한글 로그를 읽기 좋게 만드는 숫자들

어두운 테마의 바탕은 **순수한 검정이 아니라 짙은 회색**을 씁니다. Material Design의 기준값은 `#121212`입니다 ([Material Design: Dark theme](https://m2.material.io/design/color/dark-theme.html)). 위에 떠 있는 패널이나 말풍선은 바탕보다 **조금 더 밝게** 칠해 높이감을 줍니다. Apple도 뒤로 물러나는 "base" 배경과 앞으로 나오는 "elevated" 배경을 구분합니다 ([Apple HIG: Dark Mode](https://developers.apple.com/design/human-interface-guidelines/foundations/dark-mode/); [M3 Elevation](https://m3.material.io/styles/elevation/applying-elevation)). 강조색은 어두운 배경에서 **채도를 낮추고 밝게** 써야 글자가 떨려 보이는 현상이 줄어듭니다 ([Google Design: Material dark theme](https://design.google/library/material-design-dark-theme)). 글자는 새하얀 `#fff` 대신 `#e6e6e6` 정도를 쓰면 번짐이 덜합니다(관례에 따른 추론).

글자 대비의 법적·실무 기준은 2026년에도 **WCAG 2.2 AA**입니다. 본문은 **4.5:1**, 큰 글자(약 24px 이상, 굵게는 약 18.66px 이상)는 **3:1**, 입력창 테두리나 토글처럼 조작 가능한 부품은 **3:1** 이상이어야 합니다 ([W3C Understanding 1.4.11](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html)). Apple은 직접 고른 색, 특히 작은 글자에는 **7:1**을 목표로 하라고 권합니다 ([Apple HIG: Dark Mode](https://developers.apple.com/design/human-interface-guidelines/foundations/dark-mode/)). 새 대비 공식인 APCA는 WCAG 3 초안에서 2023년 7월에 빠졌고, WCAG 3는 2026-09-10 초안이 나온 단계로 정식 권고까지 몇 년이 남았습니다. 따라서 합격 기준은 여전히 WCAG 2 대비율입니다 ([Adrian Roselli: WCAG3 contrast, April 2026](http://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html); [W3C WAI: WCAG 3 WD Sept 2026](https://www.w3.org/WAI/news/2026-09-10/wcag3/)).

TRPG 로그에서 가장 흔하게 깨지는 부분은 **사용자가 고른 캐릭터 색**입니다. 흰 바탕에서 잘 보이던 짙은 남색 이름은 `#121212` 바탕에서 거의 보이지 않습니다. 그래서 캐릭터 색은 그대로 쓰지 말고, 현재 배경에 대해 대비를 계산한 뒤 **4.5:1에 못 미치면 oklch의 밝기(L)만 올리거나 내려서 보정**해야 합니다. 색상과 느낌은 유지하면서 읽을 수 있게 만드는 방식입니다. 이 보정 방법은 노트의 설계 추론이지만, 기준 수치인 4.5:1은 위의 WCAG 출처에 근거합니다. 내보낸 HTML이 "자동" 테마라면 캐릭터마다 밝은 판과 어두운 판 두 가지 색을 미리 계산해 넣어야 합니다.

한글 본문은 **최소 16px**(모바일 16~19px)이 기준입니다 ([브런치: 모바일 UI 타이포그래피 2](https://brunch.co.kr/@chulhochoiucj0/34)). 행간은 WCAG 최소 1.5, 한글 본문 권장값은 **1.75**입니다 ([리메인 디자인시스템: 행간](https://www.remain.co.kr/page/designsystem/line-height.php)). 네이버 모바일 연구에서는 **155%**가 최적이었고, 150%보다 좁으면 피로가 늘었습니다 ([브런치](https://brunch.co.kr/@chulhochoiucj0/34)). 현재 도구의 1.5~1.6은 하한선에 걸쳐 있으므로 **1.65~1.75**로 올리는 것을 권합니다. 문단 간격은 글자 크기의 약 75%(16px이면 12px)가 권장됩니다 ([리메인: font-size](https://www.remain.co.kr/page/designsystem/font-size.php)). 자간은 한글 폰트가 원래 넉넉하게 설계되어 있어 본문에서 살짝 좁히는 관례가 있습니다. 이때 `-1px` 같은 고정값보다 **em 단위 상대값**이 권장됩니다 ([uxdev.org: 한글 웹폰트 자간](https://uxdev.org/entry/%ED%95%9C%EA%B8%80-%EC%9B%B9%ED%8F%B0%ED%8A%B8-%EC%9E%90%EA%B0%84letter-spacing-%EC%9E%90%EB%8F%99%EC%9C%BC%EB%A1%9C%EC%83%81%EB%8C%80%EC%A0%81%EC%9C%BC%EB%A1%9C-%EC%A1%B0%EC%A0%95%ED%95%98%EA%B8%B0)). 원 자료의 단위가 모호하므로 `-0.01~-0.02em` 정도가 보수적인 해석입니다.

줄바꿈은 **`word-break: keep-all`**로 단어 중간에서 끊기지 않게 하되, 긴 URL이나 "ㅋㅋㅋㅋㅋ…" 같은 문자열이 상자를 뚫고 나가지 않도록 **`overflow-wrap: anywhere`를 함께** 씁니다 ([MDN word-break](https://developer.mozilla.org/en-US/docs/Web/CSS/word-break); [MDN overflow-wrap](https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-wrap)). TRPG 로그에는 웃음 반복, 다이스 결과, 링크가 흔하므로 이 조합은 필수입니다. Chrome의 `word-break: auto-phrase`는 **일본어 전용**이고 한국어는 keep-all로 충분합니다 ([Chrome for Developers: i18n CSS](https://developer.chrome.com/blog/css-i18n-features)). 이 두 속성은 인라인 스타일로도 넣을 수 있어 티스토리 코드에도 그대로 적용됩니다.

폰트는 **Pretendard v1.3.9 가변 폰트의 dynamic subset** 버전(`https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css`)이 가볍습니다. 페이지에 실제로 쓰인 글자가 든 조각만 내려받기 때문입니다 ([orioncactus/pretendard](https://github.com/orioncactus/pretendard)). 서브셋 없이 전체를 쓰면 첫 로드에 약 3MB가 들 수 있습니다 ([Moadong issue #2074](https://github.com/Moadong/moadong/issues/2074)). 티스토리 코드에서는 `<link>`를 쓸 수 없으므로 `font-family`에 `-apple-system, "Apple SD Gothic Neo", "Pretendard", "Noto Sans KR", "Malgun Gothic", sans-serif` 같은 **시스템 폰트 우선 스택**을 넣어, 블로그에 Pretendard가 없으면 기기 기본 한글 폰트로 떨어지게 합니다. 현재 도구의 폰트 스택은 이미 이 형태에 가깝습니다.

아이콘(아바타)은 채팅 UI에서 **40×40px 원형, 말풍선과 8~12px 간격**이 업계 관례입니다 ([Ahmad Shadeed: Messenger chat bubble](https://ishadeed.com/article/facebook-messenger-chat-component/); [Ionic Chat Bubble wiki](https://github.com/smukov/AvI/wiki/Ionic-Chat-Bubble)). 이 수치는 표준 기관이 아닌 실무 관례입니다. 같은 사람이 연달아 말하면 아이콘을 한 번만 보여주는 "묶기"도 표준 패턴이며, 이 도구에는 이미 "연속 발언 묶기"가 있습니다. 권장 설정 범위는 **기본 40px, 조절 32~56px**, 이름 13~14px 굵게, 대사 15~16px, 같은 화자 줄 사이 4px, 화자가 바뀔 때 12~16px입니다(노트의 추론). 스탠딩(세로형)은 아이콘이 아니라 삽화이므로 이 범위와 별도로 둡니다. 사용자가 올린 캐릭터 그림은 다크 모드에서 색을 반전시키지 말아야 하며, 밝기를 조금 낮추는 정도가 관례입니다. 다만 이를 뒷받침하는 권위 있는 출처는 이번 조사에서 찾지 못했습니다.

## 도구형 웹앱의 공통 문법: 바로 쓰고, 자동 저장하고, 되돌릴 수 있게

Squoosh, Excalidraw 같은 유명 소형 도구와 한국·일본 TRPG 로그 도구들에는 공통 문법이 있습니다. **계정 없이 첫 화면에서 드롭하면 바로 시작**하고, **설정과 결과를 나란히 보며**, **브라우저에 자동 저장**하고, **파일로 명시적인 내보내기와 가져오기**를 제공합니다 ([PCWorld: Squoosh](https://www.pcworld.com/article/3195269/googles-free-sqoosh-tool-takes-the-guesswork-out-of-image-compression.html); [DeepWiki: Excalidraw auto-save](https://deepwiki.com/excalidraw/excalidraw/6.4-local-storage-and-auto-save)). 코백은 10,000건 제한으로 잘린 코코포리아 로그 여러 개의 겹치는 부분을 알아서 이어 붙입니다 ([포스타입 코백](https://www.postype.com/en/@wwwwon/post/22211812)). 이 사례에서 보듯 **수천~수만 줄 로그가 실제로 흔하다**는 점도 설계 전제로 삼아야 합니다.

**설정 패널**은 "기본 / 캐릭터 / 색·글꼴 / 고급 / 내보내기"처럼 묶어서 `<details>`로 접습니다. 같은 `name`을 주면 하나를 열 때 나머지가 자동으로 닫히는 아코디언이 되며, 이는 Chrome 120, Safari 17.2, Firefox 130부터 지원하는 Baseline 2024 기능입니다 ([MDN blog: exclusive accordions](https://developer.mozilla.org/en-US/blog/html-details-exclusive-accordions)). 여러 묶음을 동시에 펴 두고 비교하는 경우가 잦다면 `name`을 빼면 됩니다. 선택지가 2~4개인 옵션(레이아웃, 배경, 아이콘 모양)은 드롭다운보다 한눈에 보이는 버튼 묶음(세그먼트 컨트롤)이 낫다는 것이 일반 관례입니다. 다만 이를 뒷받침하는 최신 NN/g 원문은 확보하지 못했습니다.

**대사 삭제나 설정 초기화**에는 "정말 삭제할까요?" 확인창을 띄우기보다 **즉시 실행한 뒤 "되돌리기" 알림**을 보여주는 쪽이 권장됩니다. NN/g는 확인창을 자주 띄우면 사용자가 읽지 않고 누르는 습관이 생긴다고 지적합니다 ([NN/g Confirmation Dialogs](https://www.nngroup.com/articles/confirmation-dialog/)). 되돌릴 수 없는 일, 예를 들어 새 로그를 불러와 지금까지의 편집을 덮어쓰는 경우에만 확인을 받거나 덮어쓰기 전에 자동 백업합니다. 현재 도구의 "삭제/되살리기"는 이미 이 철학에 가깝습니다.

**대사 수정 다이얼로그**는 네이티브 `<dialog>`와 `showModal()`로 계속 만드는 것이 맞습니다. 포커스를 창 안에 가두고, ESC로 닫고, 닫은 뒤 원래 위치로 포커스를 돌려주는 일을 브라우저가 대신 해 줍니다 ([MDN `<dialog>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog)). "복사됨", "저장됨" 같은 알림은 **처음부터 페이지에 빈 채로 있는 `role="status"` 영역**에 글자를 넣는 방식이어야 화면 낭독기가 제대로 읽습니다. 알림 영역을 그때그때 새로 만들면 읽히지 않거나 두 번 읽힐 수 있습니다 ([Sara Soueidan: ARIA live regions](https://www.sarasoueidan.com/blog/accessible-notifications-with-aria-live-regions-part-1/)). 알림으로 포커스를 옮기거나 너무 빨리 사라지게 하는 것도 흔한 실수입니다 ([accessibility.build](https://accessibility.build/guides/accessible-notifications)). 키보드 초점 표시는 2px 두께와 3:1 대비를 갖추면 AAA 기준(2.4.13)까지 적은 비용으로 충족합니다 ([W3C Understanding 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)).

**모바일**에서는 WCAG 2.2 AA가 터치 대상 최소 **24×24 CSS px**을 요구하고, AAA 기준은 **44×44px**입니다 ([wcag22aa.org: target size](https://wcag22aa.org/new-criteria/target-size/)). 설정 패널의 버튼과 체크박스는 44px을 목표로 잡습니다. 주소창이 나타났다 사라지며 화면 높이가 어긋나는 오래된 `100vh` 문제는 **`100dvh`**로 해결됩니다. dvh는 2025년 6월 Widely가 되었습니다 ([OpenReplay: 100vh](https://blog.openreplay.com/fix-100vh-mobile-viewport/)). 아이폰 하단 막대에 버튼이 가리지 않도록 `env(safe-area-inset-bottom)`을 함께 씁니다. NN/g는 바텀 시트를 "잠깐 쓰는 보조 조작"에만 쓰고 늘 필요한 도구나 긴 내용에는 쓰지 말라고 합니다 ([NN/g Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/)). 따라서 좁은 화면에서는 **하단 탭 [설정 | 미리보기 | 내보내기]로 화면 전체를 전환**하고, 바텀 시트는 대사 한 줄 수정 같은 짧은 작업에만 쓰는 구성을 권합니다(추론). 조사한 한국 TRPG 도구들의 모바일 지원 수준은 확인하지 못했습니다. 모바일에서 제대로 쓰이는 것 자체가 차별점이 될 가능성이 있습니다.

**자동 저장**에는 분명한 한계가 있습니다. localStorage는 약 **5MB**가 한계이고, Excalidraw에서도 실제 문제로 지적되었습니다 ([DeepWiki: Excalidraw](https://deepwiki.com/excalidraw/excalidraw/6.4-local-storage-and-auto-save)). Safari는 사용자가 **7일 동안 그 사이트와 상호작용하지 않으면** localStorage와 IndexedDB를 포함한 스크립트 저장소를 지웁니다. 홈 화면에 추가한 웹앱은 예외입니다 ([lapcatsoftware](https://lapcatsoftware.com/articles/2023/8/5.html); [selfstore: browser storage is not durable](https://selfstore.dev/blog/browser-storage-is-not-durable)). 이 정책이 2025~2026년에 바뀌었는지는 확인하지 못했습니다. 그래서 설정과 프리셋처럼 작은 데이터는 localStorage에, 로그 원문과 편집 결과처럼 큰 데이터는 IndexedDB에 둡니다. 입력 후 약 0.5초 뒤, 그리고 탭이 숨겨질 때 저장합니다. 다시 열면 **"지난 작업을 복원할까요?"**라고 묻고, **"설정 파일(JSON) 내보내기/가져오기"를 진짜 백업 수단으로** 제공하는 구성을 권합니다. Excalidraw 사용자들이 자동 저장이 불투명하다고 불만을 제기한 사례를 보면 ([Excalidraw Discussion #6463](https://github.com/excalidraw/excalidraw/discussions/6463)), "3초 전 자동 저장됨" 같은 상태 표시도 효과가 있습니다.

**내보내기와 복사**는 `<a download>` + Blob이 모든 브라우저에서 통하는 기본 경로입니다. 저장 위치를 고르는 `showSaveFilePicker`는 여전히 **Chrome·Edge 전용**이고 Firefox와 Safari는 지원하지 않습니다 ([caniuse: File System Access](https://caniuse.com/native-filesystem-api)). 서식 있는 HTML을 클립보드에 넣는 `ClipboardItem`은 2024년 6월에 Baseline이 되었습니다 ([MDN Clipboard.write](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/write)). 티스토리용 "코드 복사"는 소스 문자열이 필요하므로 `writeText()`가 맞습니다. 두 용도를 버튼으로 구분하면 헷갈림이 줄어듭니다. PWA로 만들어 오프라인에서도 쓰게 하려면 서비스 워커를 별도 파일로 두어야 해서 단일 파일 원칙과 충돌합니다. 따라서 GitHub Pages 배포판의 선택 사항으로 남겨 두는 것이 현실적입니다(추론).

**성능**에서 가장 값싼 한 수는 **`content-visibility: auto`**입니다. 화면 밖 요소의 배치와 그리기를 건너뛰는 기능으로, 2024년 9월 Safari 18 지원과 함께 Baseline이 되었습니다. web.dev 예제에서는 초기 렌더링이 **약 7배** 빨라졌습니다 ([web.dev: content-visibility Baseline](https://web.dev/blog/css-content-visibility-baseline); [web.dev: content-visibility](https://web.dev/articles/content-visibility)). 미리보기 iframe 안의 대사를 50~100개씩 묶은 덩어리에 `content-visibility:auto; contain-intrinsic-size:auto 60px`를 적용하고, 설정을 바꾸면 150~300ms 뒤에 미리보기를 갱신합니다. 색 변경처럼 CSS 변수만 바뀌는 경우에는 iframe 전체를 다시 쓰지 말고 변수만 고치면 스크롤 위치도 유지됩니다(추론). 긴 파싱 작업 중간에 화면을 멈추지 않게 하는 `scheduler.yield()`는 Chrome/Edge 129 이상에서만 확실히 동작하므로 `setTimeout` 대체가 필요합니다 ([MDN Scheduler.yield](https://developer.mozilla.org/en-US/docs/Web/API/Scheduler/yield)). 참고로 `content-visibility`는 `<style>` 없이 인라인 속성으로도 쓸 수 있으므로 티스토리 코드에도 넣을 수 있습니다.

## 이 도구에 적용할 순서: 효과는 크고 위험은 작은 것부터

아래 우선순위는 세 가지 기준으로 정했습니다. 사용자가 매번 체감하는지, 현재 코드에서 빠진 부분인지, 구형 브라우저에서 망가질 위험이 적은지입니다. 순위 판단 자체는 이 보고서의 해석이며, 각 항목의 근거 수치와 출처는 위 본문에 있습니다.

| 순위 | 할 일 | 왜 지금인가 | 난이도 |
|---|---|---|---|
| 1 | 도구 테마 3단 선택(시스템/밝게/어둡게) + `<head>` 인라인 스크립트로 깜빡임 방지 + `color-scheme` 선언 | 현재는 OS만 따라가 수동 선택이 불가. 모든 사용자가 매번 체감 | 낮음 |
| 2 | 캐릭터 이름·글자색 대비 자동 보정(배경 대비 4.5:1 미만이면 oklch 밝기 조정) | 어두운 배경에서 이름이 사라지는 것이 로그 가독성의 최대 실패 원인 | 중간 |
| 3 | 내보낸 HTML에 "자동(보는 사람 따라)" 테마 추가. `@media` 변수 방식을 기본으로, `light-dark()`는 보강용 | 독자 쪽 다크 모드 대응. 오래된 인앱 브라우저까지 안전 | 중간 |
| 4 | 본문 타이포 정비: 16px, 행간 1.65~1.75, `keep-all` + `overflow-wrap:anywhere`, 문단 간격 0.75em | 인라인으로도 적용되어 HTML과 티스토리 양쪽에 곧바로 효과 | 낮음 |
| 5 | 자동 저장(설정은 localStorage, 로그는 IndexedDB) + 복원 배너 + 설정 JSON 내보내기/가져오기 + 저장 상태 표시 | 긴 작업 중 새로고침·탭 닫기로 편집이 날아가는 것을 방지. Safari 7일 삭제에 대비 | 중간 |
| 6 | 미리보기에 `content-visibility:auto` 청크 적용, 설정 변경 디바운스, CSS 변수만 부분 갱신 | 10,000줄급 로그에서 체감 속도 개선. 한 줄 CSS로 큰 효과 | 낮음 |
| 7 | 모바일: `100dvh`, safe-area 여백, 터치 대상 44px, 좁은 화면 하단 탭 전환 | 조사한 경쟁 도구 대비 차별화 여지 | 중간 |
| 8 | 접근성 마감: 정적 `role="status"` 알림 영역, `:focus-visible` 2px 윤곽선, 삭제는 확인창 대신 되돌리기 | 적은 비용으로 WCAG 2.2 AA 이상 충족 | 낮음 |
| 9 | 티스토리 "자동 테마(실험적)": 감싸는 상자에 인라인 `color-scheme` + `light-dark()` + 일반 색 대비책 | 미디어쿼리 없이 양쪽 테마를 지원할 유일한 길. 먼저 편집기 테스트 필요 | 중간(검증 필요) |
| 10 | 코드 정리: CSS 중첩·`@layer`, 설정 묶음 `<details name>`, invoker commands(구형 Safari용 JS 대체 유지) | 기능 변화는 적지만 1,440줄 단일 파일의 유지보수성이 좋아짐 | 낮음~중간 |

| 보류 | `closedby`, `popover="hint"`, `interpolate-size`, 커스텀 `<select>`, `text-wrap: pretty`에 기능을 의존하는 것 | 2026년 9월 기준 한 개 이상의 주요 브라우저에 없음 | — |

아바타 크기는 우선순위 표와 별도로, 기본값을 40px로 맞추고 조절 범위를 32~56px로 제한하는 정도면 충분합니다. 현재 도구에 이미 크기 조절이 있으므로 기본값만 점검하면 됩니다.

## Conclusion

이번 조사에서 가장 달라진 판단은 "다크 모드"가 한 가지 문제가 아니라 **세 곳에서 따로 풀어야 하는 문제**라는 점입니다. 도구 화면은 최신 브라우저만 가정해도 되므로 `light-dark()`와 인라인 head 스크립트로 깔끔하게 끝납니다. 내보낸 HTML은 누가 어떤 브라우저로 열지 모르므로 `@media` 방식을 바닥에 깔아야 합니다. 티스토리 코드는 규칙을 못 쓰는 대신 속성값은 쓸 수 있다는 틈을 노려야 합니다. 그리고 세 곳 모두에서 진짜 병목은 테마 전환 장치가 아니라 **사용자가 고른 캐릭터 색의 대비**입니다. 테마 토글만 달고 색 보정을 빼면, 다크 모드를 켜는 순간 로그가 읽히지 않게 됩니다.

더 넓게 보면, 2026년의 브라우저는 단일 파일 도구에 유리한 쪽으로 움직였습니다. 대화상자, 아코디언, 버튼-창 연결, 다크 모드 색 전환, 긴 목록 최적화가 모두 HTML/CSS 한 줄 수준으로 내려왔습니다. 그만큼 JS는 로그 파싱, 표정 연결, 저장 같은 이 도구만의 핵심 로직에 집중할 수 있습니다. 남은 불확실성은 두 가지입니다. 티스토리 편집기가 `color-scheme`·`light-dark()`·`content-visibility` 인라인 속성을 보존하는지, 그리고 Safari의 7일 저장소 삭제 정책이 여전히 유효한지입니다. 둘 다 짧은 실측으로 확인할 수 있으므로, 9순위 작업에 앞서 먼저 검증하는 것이 좋습니다.
